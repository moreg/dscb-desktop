# 续写首稿叙事排查

## 版本与现场

- 检查起点为 `master` 的 `3a850fd`，源码应用版本为 `0.1.58`。工作区原有未跟踪备份留在本机。
- 本机运行的桌面主进程从此仓库以 `electron.exe .` 启动。它使用的本地 `out/main/index.js` 仍包含旧的执行清单标记。磁盘上的 Web 构建也含旧标记，本机未查到该 Web 服务进程，无法据此判断外部 Web 部署。
- 本机桌面配置的 `autoDeslopAfterContinue` 为 `false`，已有两项自定义写作规则。本次故障对应的原始请求和单次开关快照不可回溯，不能据当前配置反推每一轮的参数或当时有无细纲。

## 实际请求路径

| 入口 | 路径与返回方式 |
| --- | --- |
| 桌面与完整 Web（包括移动浏览器） | 章节编辑器 → preload 或 Web IPC 桥 → `write:generateChapter` → `deliverChapter` → `generateChapterStream`。模型增量用于预览，最后采用带保存回执的整章。 |
| 手机局域网配对页 | 单章 AI 路由直接调用 `generateChapterStream` 的候选模式。返回新增正文及整章拼接结果，采用后才按版本保存。 |
| 桌面、Web 与手机批量 | 各批量入口 → `generateChaptersBatch` → `runFullFlowForChapter` → 同一正文生成器。批量验收需要细纲，继续保留补纲和恢复能力。 |
| 按要求重写 | `adjustChapterStream` 使用完整原稿、当前要求或已确认方案，以及作品规则、文风和相关历史。按原有重写契约返回整章稿，手机先给候选。 |

`WriteService.buildChapterPrompt` 组合两条消息。系统消息承载作者自定义正负规则、文风档案的分析结果和默认落笔规则，用户消息带作品设定、可用历史证据、已有正文、实际存在的章节计划、作者要求与字数。文风档案的原始分析样本文本留在档案中，生成使用档案的视角、句式、语气等分析字段。同章已写前部仍完整传入，超预算明确拒绝。CLI 模型会合并两条消息，HTTP 模型按协议映射角色。Antigravity 超预算时可裁剪背景，本章前部、任务和作者自定义规则保留为必须完整提交的区块。

首稿返回后会剥离非正文回执、整理空白和误入正文的出版章号，再拼接新增片段。格式化按现有规则保留句序和句段，续写前部逐字只读。事实、章界和必要伏笔仍可能进入既有核对和修复流程。自动去 AI 味关闭时，生成链跳过表达润色。按要求重写走既有的独立流程。

## 发现与修改

- **确认的代码问题**。旧单章交付会先补缺失细纲，再把计划反复放入细纲正文、执行清单和写前写后自检。旧无纲预览仍会收到默认细纲指令。旧章节要求解析还可能把行首小数或数量当作编号剥掉。
- **原因判断**。重复任务与默认从细纲逐项推进，会提高模型把场景写成操作队列的风险。它们不能单独证明是该样稿的成因。格式化不按动作拆句或补写心理，已知该稿也未启用自动润色。
- [write-service.ts](../src/main/data/write-service.ts) 把单章无纲写作与批量补纲分开。本章计划、禁区和章节要求各提供一次，保留历史原文、章界、能力限制及既有字数口径。无纲时，已发现的事实冲突仍可按已有正文修复与复核。
- [index.ts](../src/main/data/skill-prompts/index.ts)、[chapter-rules.ts](../src/main/data/skill-prompts/chapter-rules.ts) 和 [scene-naturalness.ts](../src/main/data/skill-prompts/scene-naturalness.ts) 收束生成规则，按人物目的、压力、感受、选择和后果组织连续动作。可压缩次要操作，但须保留必要步骤、数字、空间、因果和结果。短句仍可自然使用，单次失效只支持对应条件内的判断，人物可以误判而旁白不得把推测当事实。
- [writing-requirement-templates.ts](../src/shared/writing-requirement-templates.ts) 只去除真正的列表标记，保留 `17.5 秒` 这类规则的数字。原设置、旧项目和对外调用参数可继续使用，无须迁移。回退时以此次改动的源码差异为单位，恢复到本次检查起点的行为。
